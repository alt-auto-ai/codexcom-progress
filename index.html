What carries the messages?

Codex’s MCP client calls the CODEXCOM MCP server. Authenticated requests reach the Ubuntu Hub through SSH tunnels; workers use native Codex queue and observation mechanisms to deliver work into extension-owned chats and report results. The controller schedules a correlated continuation after the required completion evidence.

The implementation uses a TypeScript/Node.js Hub and workers, HTTP APIs, WebSocket events, SQLite persistence and local worker journals. Sharing one Codex account does not connect the chats automatically. The temporary Shared folder carries setup artifacts only.

DIR and WRX execute on Ubuntu through remote VS Code workspaces displayed on the laptop. ZEN executes locally on the laptop; WIN executes locally in the VM. A directory selects a workspace; it does not by itself establish a security boundary.

Last reported operating posture: services stopped following the owner’s shutdown, dispatch hold persisted, no pending work and historical records preserved. Hub automatic startup was disabled; workers and SSH tunnels were manually launched. This page does not poll runtime health.

Roadmap to CODEXCOM production reliability

Method: execute a small useful workload → inspect observed failures → make the smallest correction → rerun the affected step. Reuse passing evidence, avoid broad repeated campaigns, and preserve uncertain work instead of blindly replaying it.

  1. Current — complete DIR supervision. Bind the exact DIR and WRX chats to their approved workspaces, retain WIN’s proven chat, configure role-scoped MCP credentials, qualify changed enforcement paths and activate the reviewed build. Prove the five-turn delegation/review/continuation/report loop with one useful artifact.
  2. Owner-controlled work sessions. Prove closed-by-default admission, owner-only session start, DIR admission/drain controls within that grant, expiry and task/turn budgets. Cover every controller/worker continuation and prevent self-granted sessions. Distinguish normal drain from emergency cancellation; the initial manual UI turn’s reserved slot is accounting, not a technical block on additional human UI input.
  3. Native progress, requests and “Ask and continue”. Finish Stage 08 live observation and expose the actual pending approval or clarification with stable identity and scope. Distinguish native execution, accepted report and local ACK; retain unknown when unobserved. Prove approve, deny, delayed response and continuation without confusing denial with task cancellation.
  4. Delivery and dependency reliability. Prove duplicate suppression, correlation, ordering tolerance, complete-result requirements, cancellation races and stale-binding rejection under useful workloads. Exercise missing/late results and uncertain submission without blind replay. Integrate dependency review and final coordinator reporting.
  5. Recovery across OS and machine boundaries. Demonstrate same-identity Hub/worker restart, tunnel loss/reconnect, lease recovery, process interruption, report retry and continued observation of extension-owned work. Reconcile ambiguous outcomes before resubmission; preserve history and quarantine.
  6. Authority and confinement. Validate project boundaries with native sandbox and OS enforcement, credential isolation for co-located roles, least-privilege tools, token rotation/revocation and escalation to the owner for privileged actions. Test that peer content cannot grant authority or escape the approved objective.
  7. Bounded scale and economical operation. Exercise concurrent operators, backpressure, per-agent limits, long waits and larger context using small representative tasks. Record latency, failure rates and token/usage data where available. Use the cheapest capable available models, preserve manual settings and escalate model capability only when measured need justifies it.
  8. Operational release acceptance. Verify reproducible cross-platform builds, native-version compatibility, dependency setup, backup/restore, contract/data migrations, rollback, sanitized diagnostics and controlled startup/shutdown. Run a representative workload through failure and recovery before accepting production operation; add unattended startup only with explicit owner policy.

Release decision

Production readiness requires passing evidence for authorized execution, correct results, durable acknowledgement, recovery, confinement and owner control on the supported topology. No completion percentage or reliability guarantee is inferred from a single pilot or test count.

The owner authorizes work sessions; DIR coordinates within them and reports progress, blockers and consequential decisions. The intended supervisor can start or stop operators within that authorization, but cannot open its own owner session. Further-agent lifecycle control remains to be proven.

Separate future project · enduring direction

ACTOR — Autonomous Autopoietic AI Organisation

Make the organisation the persistent entity. Agents, models and runtimes should be replaceable without losing the organisation’s identity, authority, relationships, knowledge or accumulated experience.

CODEXCOM remains its own communication and reliability project. Its validated mechanisms are a stepping stone for ACTOR, whose initial emphasis is multiple specialist agents on one Ubuntu workstation, with cross-machine and cross-OS operation available as a later scalability option.

Durable institutional kernel

Own the organisational registry, role identities, channel definitions, authority rules, durable event history and lifecycle management. Build in versioned contracts, migrations and recovery so foundational change can be rare and controlled.

  • Recursive organisational structure with consistent principles at each viable unit.
  • Stable communication semantics independent of the participating agent implementation.
  • Persistent institutional memory for knowledge, decisions, outcomes and history.
  • Explicit purpose, responsibility, permissions and escalation boundaries.
  • Continuous feedback that detects deviations and supports correction and adaptation.
  • Controlled introduction, evaluation and incorporation of new capabilities.

What CODEXCOM can contribute

Native Codex execution, visible persistent chat workplaces, correlated task/result contracts, automatic continuation, cross-platform worker adapters and durable journals. Supervision, owner-session gates, safe drain, recovery and observability will become reusable mechanisms as their respective proofs are completed.

Dedicated chats and directories provide owner-visible workplaces for observing and guiding agents. They are not substitutes for access control or institutional memory. A permanent organisational role should retain its purpose, authority and evaluated experience across replacement agents.

NATS / JetStream: planned for ACTOR channels where suitable. It is not the transport used by the demonstrated CODEXCOM pilots, and no NATS integration is claimed here. Codex remains the intended agent execution platform.
